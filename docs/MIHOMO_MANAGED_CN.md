# 网页管理 Mihomo（2.7.3 开发中）

在系统设置的 Codex 打票代理区选择 Mihomo，点击「检测并安装」。安装完成后填写 Clash/Mihomo YAML 订阅地址，点击「保存并应用」。运行就绪后点击「设为打票代理」并保存系统设置。多订阅可逐行输入或导入 TXT；可追加或替换，空输入保留已保存订阅并重新获取节点。

内核在 Sub2API 数据目录的 `mihomo-codex` 子目录运行，使用应用用户，不需要 sudo。当前支持 Linux amd64/arm64。内核版本固定为 v1.19.31，通过官方 Release asset 的 SHA-256 摘要校验；订阅仅导入 outbound proxies，不导入订阅里的监听器、规则和控制接口。

订阅 URL、节点凭据和控制器 secret 保存于权限 0600 的文件，API 不回显这些内容。更换配置前先获取节点并运行内核配置检查；配置失败保留旧设置。启动任务互斥且可查询，应用退出时关闭内核，应用启动时恢复已保存的内核配置。

节点支持连接检测、停用和手动恢复。失败/停用节点从轮换组移出；全节点停用时使用 REJECT，避免落到直连。节点显示名是匿名标识；enabled 只代表允许参加轮换，不保证网络连通。没有“用后移出”策略。订阅当前通过「保存并应用」刷新，不在后台定时重新下载。

静态住宅代理单独保留最后保存的 URL，可从内核切回，并继续使用已有脱敏与热更新机制。账号业务代理不会因此改变。

后台提供「提前准备备用」与「固定主用」策略；默认保留提前刷新行为，切换不清除有效票据或冷却。账号编辑区及列表提示可查看最近采集结果、HTTP 状态、下次允许探测时间和备用有效期。账号额度限流期间不执行采集。

## 旧 systemd 内核迁移

root 二进制安装/升级流程检测到旧机场服务后，调用 `migrate-mihomo-managed.sh`：暂存旧订阅与节点缓存、生成新的控制凭据、验证内核配置，再切换服务。原配置和缓存保留。新内核通过带凭据的本机检查后才关闭旧服务的开机启动；切换失败则保留失败目录、恢复旧代理并重新启动应用。

默认应用目录和数据目录为 `/opt/sub2api`；自定义数据目录需将实际的 `DATA_DIR` 传给升级脚本。已有受管目录不会覆盖。迁移只识别旧安装器创建的单个 airport provider；自定义旧内核配置需人工迁移。迁移暂存目录与目标目录跨文件系统时会安全失败，旧代理尚未停止。

## 当前限制及发布前工作

- 仅网页二进制自更新没有 root 权限，不能执行旧 systemd 服务迁移；需要经 root 升级入口完成一次迁移。网页不会尝试提权或覆盖现存内核。
- 没有实测 ARM64、Docker 部署或真实机场/模型请求；Linux amd64 的内核安装、模拟订阅应用、失败保留和重启恢复已在隔离目录验证。
- 网页组件以模拟 API 做浏览器交互测试，不等同已验证完整生产认证链路。
- ticket 侧已实现结构化完成事件校验、候选时间校验、公平轮询、主备缓存和 HTTP 响应头形态异常后的撤销/提升。不重放当前业务请求；没有严格正文拦截开关，也未覆盖 WebSocket 业务反馈。
- 节点用后移出、严格响应处理仍待实现；迁移的 systemd 切换尚未在真实机器验证，开发分支尚不作为可发布的 2.7.3。

## 验证方式

常规测试使用本地模拟服务：`go test -race ./internal/mihomo`。

可选官方内核安装冒烟测试：`MIHOMO_INSTALL_SMOKE=1 go test ./internal/mihomo -run TestOfficialKernelInstallation -v -count=1`。该测试下载官方内核，订阅和出口均使用本地模拟服务，不调用模型、不使用生产订阅或更改生产服务。
